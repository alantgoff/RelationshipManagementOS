# ADR-0002: v1 architecture

Date: 2026-09-12
Status: Accepted
Implements: `docs/specs/0001-v1-core.md`

## Context
v1 is a single-owner app with a small, well-defined domain. The architecture
must keep data access owner-scoped by construction, make the health rules
unit-testable without a database, and stay small enough for one developer.

## Decisions

### Runtime
- Next.js 16 App Router (ADR-0001 said 15; 16 is current stable and the
  only version `create-next-app` scaffolds). Server Components for reads,
  Server Actions for writes. No separate API layer in v1.
- Clerk 7 for auth via `proxy.ts` (Next 16's name for middleware) and
  `auth()` in server code.
- Drizzle ORM over `postgres` (postgres-js). One driver in every environment.
  Migrations generated by drizzle-kit into `src/db/migrations` and applied by
  `scripts/migrate.ts`.

### Module layout
```
src/
  app/                 routes only; thin, call queries/actions
    (app)/             authenticated shell: dashboard, people, import, settings
    sign-in/           Clerk sign-in
  components/          presentational + small client components
  db/
    schema.ts          Drizzle tables and enums
    client.ts          lazy postgres-js + drizzle instance
    migrations/        generated SQL
  domain/              pure functions, no I/O: health, cadence, csv mapping
  server/
    auth.ts            requireUserId()
    queries/           owner-scoped reads
    actions/           owner-scoped writes ("use server"), zod-validated
tests/
  unit/                domain functions
  integration/         queries + actions against a real Postgres
  e2e/                 Playwright, acceptance criteria AC-1..AC-10
```

### Owner scoping
Every table has `user_id`. Every query and action calls `requireUserId()`
and filters on it. No query helper accepts a user id from the caller; it is
always read from the session. This is the mechanism behind AC-9.

### Health
`domain/health.ts` exports `computeHealth({ cadenceDays, lastInteractionAt, now })`
and `defaultCadenceForRoles(roles)`. Queries fetch `max(interactions.occurred_at)`
per person in SQL and pass it to the pure function. No stored health column.

### Search
Postgres full-text via a generated `tsvector` column on `people`
(name, company, email) and on `interactions` (summary, notes), plus tag
names. One query unions the three and returns distinct people.

### Dev auth fallback
When Clerk keys are absent and `NODE_ENV !== "production"`, `requireUserId()`
returns `DEV_USER_ID` from env (default `dev-user`). This lets tests and local
dev run without Clerk. In production, missing keys fail the build.

## Consequences
- No background jobs; health is computed on read. Fine to a few thousand people.
- Server Actions couple UI to Postgres. Acceptable for a single-owner app;
  a v2 API can wrap the same `server/queries` and `server/actions` modules.
- Integration tests need a Postgres. CI uses a service container.
