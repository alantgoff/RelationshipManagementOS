# Spec 0001: RelationshipManagementOS v1 Core

Date: 2026-09-12
Status: Draft for review
Stack: see `docs/adr/0001-stack.md`

## 1. Purpose

A single-user relationship manager that keeps the right people warm. It is a
personal tool first (friends, family, mentors) and a fund tool second: the
owner is starting a VC microfund and needs prospective LPs, deal-flow sources,
founders, and co-investors to stay engaged without a sales-style CRM.

The product answers three questions every time it is opened:

1. Who am I going cold on, and how badly?
2. What did we last talk about, and what did I promise?
3. Who should I reach out to this week, and why?

## 2. Scope

### In scope for v1
- Single owner account (Clerk auth). No sharing, no team features.
- People, interactions, cadences, roles/tags, reminders, health score.
- A "This week" dashboard driven by cadence and health.
- Manual data entry plus CSV import of people.
- Fund-specific fields: LP prospect stage, deal-source quality, intro tracking.
- Full-text search across people and interaction notes.

### Out of scope for v1
- Email or calendar sync, LinkedIn scraping, any automated ingestion.
- Multi-user, permissions, or shared workspaces.
- Pipeline or deal management (companies, rounds, cheque sizes).
- Mobile apps. The web app must be usable on a phone browser.
- AI drafting of messages. Reserved for v2 once the data model is stable.

## 3. Personas and jobs

| Persona | Job to be done |
|---|---|
| Owner as friend | Not let months slip by with people who matter. |
| Owner as emerging GP | Keep 30 to 80 prospective LPs warm over a 12 to 18 month raise. |
| Owner as deal sourcer | Remember which founders, angels, and operators send good deals, and reciprocate. |

## 4. Domain model

All entities belong to exactly one owner (`userId` from Clerk). Timestamps are
UTC. IDs are UUIDv7.

### Person
| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| fullName | text | required |
| preferredName | text | optional, used in UI |
| email, phone | text | optional |
| company, title | text | optional |
| location | text | free text, optional |
| howWeMet | text | optional |
| notes | text | markdown, long-form |
| roles | Role[] | zero or more, see below |
| cadenceDays | int | desired days between touches; null = no cadence |
| lpStage | enum | null unless role includes `prospective_lp` |
| dealSourceQuality | enum | null unless role includes `deal_source` |
| archivedAt | timestamp | soft delete |
| createdAt, updatedAt | timestamp | |

Derived, not stored: `lastInteractionAt`, `daysSinceContact`, `health`.

### Role (enum, multi-select)
`friend`, `family`, `mentor`, `prospective_lp`, `committed_lp`, `deal_source`,
`founder`, `co_investor`, `service_provider`, `other`.

### LpStage (enum)
`identified`, `intro_made`, `first_meeting`, `data_room`, `soft_commit`,
`committed`, `passed`. Only meaningful when role includes `prospective_lp`
or `committed_lp`. Moving to `committed` auto-adds role `committed_lp`.

### DealSourceQuality (enum)
`unknown`, `low`, `medium`, `high`. Set manually. v1 does not compute it.

### Tag
Free-form labels (`YC alum`, `Boston`, `climate`) owned by the user.
Many-to-many with Person. Roles are structured; tags are not.

### Interaction
| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| personId | uuid | required |
| type | enum | `call`, `meeting`, `email`, `message`, `intro`, `event`, `note` |
| occurredAt | timestamp | required, defaults to now |
| summary | text | one line, required |
| notes | text | markdown, optional |
| followUps | FollowUp[] | zero or more |
| createdAt | timestamp | |

An `intro` interaction may reference a second person via `introducedPersonId`.
This is how intro tracking works in v1: who introduced whom, and when.

### FollowUp (promise made during an interaction)
| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| interactionId | uuid | |
| description | text | required |
| dueAt | timestamp | optional |
| completedAt | timestamp | null until done |

### Reminder
| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| personId | uuid | |
| dueAt | timestamp | required |
| reason | text | e.g. "birthday", "check in after fund close" |
| completedAt | timestamp | |
| snoozedUntil | timestamp | |

Cadence-driven nudges are computed, not stored as Reminders. Reminders are
explicit, one-off items the owner sets.

### RelationshipHealth (computed)
Input: `cadenceDays`, `daysSinceContact`.

| Health | Rule |
|---|---|
| `no_cadence` | cadenceDays is null |
| `fresh` | daysSinceContact <= 0.5 * cadenceDays |
| `warm` | 0.5 * cadenceDays < daysSinceContact <= cadenceDays |
| `due` | cadenceDays < daysSinceContact <= 1.5 * cadenceDays |
| `cold` | daysSinceContact > 1.5 * cadenceDays |
| `never` | cadence set but no interactions ever |

Default cadences applied when a role is first added and cadenceDays is null:
`prospective_lp` 21, `committed_lp` 45, `deal_source` 30, `founder` 45,
`co_investor` 60, `mentor` 60, `friend` 45, `family` 30. The owner can
override per person. If a person has several roles, the shortest default wins.

## 5. Functional requirements

Priority: P0 must ship in v1, P1 should, P2 if cheap.

### People
- FR-1 (P0) Create, edit, archive, and restore a person. Archived people are hidden from lists and health by default.
- FR-2 (P0) Assign multiple roles and tags. Roles apply default cadence per section 4.
- FR-3 (P0) Person detail page shows profile, health, interaction timeline (newest first), open follow-ups, and reminders.
- FR-4 (P0) Import people from CSV with column mapping for name, email, phone, company, title, roles, tags, cadence. Duplicate detection on exact email match; the user picks merge or skip.
- FR-5 (P1) Merge two people, keeping all interactions and the union of tags and roles.

### Interactions
- FR-6 (P0) Log an interaction from the person page or the dashboard in under 3 fields: type, summary, date (defaults now).
- FR-7 (P0) Add follow-ups to an interaction, mark them complete, see open ones on the person page and dashboard.
- FR-8 (P0) An `intro` interaction can link a second person. Both people's timelines show it.
- FR-9 (P1) Edit and delete interactions. Deleting removes its follow-ups.

### Cadence, health, and dashboard
- FR-10 (P0) Every person with a cadence gets a computed health state per section 4. Health recomputes on read; no background jobs in v1.
- FR-11 (P0) Dashboard "This week" lists people in order: `cold`, then `due`, then `never`, tie-broken by shortest cadence. Each row shows name, roles, days since contact, last summary, and a one-click "Log interaction".
- FR-12 (P0) Dashboard shows open follow-ups due within 7 days and overdue, and explicit reminders due within 7 days.
- FR-13 (P1) Filter the dashboard by role, so the owner can view "LP raise" and "friends" as separate lists.
- FR-14 (P2) Weekly summary email of the dashboard, sent Monday morning in the owner's timezone.

### Fund features
- FR-15 (P0) Set and change `lpStage` on people with an LP role; the person list can group by stage as a simple kanban or grouped table.
- FR-16 (P0) Set `dealSourceQuality` on deal sources; the people list can sort by it.
- FR-17 (P1) A person page shows "Intros given" and "Intros received" counts derived from `intro` interactions.

### Search
- FR-18 (P0) Search box matches person name, company, email, tags, and interaction summaries and notes. Postgres full-text search is sufficient.

### Account
- FR-19 (P0) Sign in with Clerk. All queries are scoped by `userId`; there is no path that reads another user's rows.
- FR-20 (P1) Export all data as JSON and CSV.

## 6. Non-functional requirements

- NFR-1 Dashboard renders in under 1 second at 500 people and 10,000 interactions on Vercel with a Neon or Supabase Postgres.
- NFR-2 Works on a phone browser at 390px width. Logging an interaction must be doable with one thumb.
- NFR-3 Data is private to the owner. No analytics on content. Clerk session required for every route except sign-in.
- NFR-4 Schema changes only through checked-in Drizzle migrations.
- NFR-5 Unit tests for health calculation, default cadence resolution, and CSV mapping. E2E test for: sign in, create person, log interaction, see them leave the dashboard.
- NFR-6 Accessible: keyboard-navigable forms, labelled inputs, sufficient contrast.

## 7. Key screens

1. **Dashboard** ("This week"): health-ordered people list, open follow-ups, reminders, role filter, quick-log button.
2. **People**: searchable table with role and tag filters, sort by health, name, last contact, deal-source quality. Toggle to LP stage grouping.
3. **Person detail**: header with health badge and cadence, timeline, follow-ups, reminders, edit drawer.
4. **Log interaction** (modal or bottom sheet): type, summary, date, optional notes and follow-ups, optional introduced person.
5. **Import**: upload CSV, map columns, preview, resolve duplicates, confirm.
6. **Settings**: default cadences per role, timezone, export.

## 8. Acceptance criteria

The v1 build is done when all of these pass:

- AC-1 A new user signs in, creates a person with role `prospective_lp`, and sees cadence 21 applied automatically.
- AC-2 That person appears on the dashboard as `never`. After logging a meeting, they disappear from the dashboard and show `fresh` on their page.
- AC-3 Setting the meeting date to 30 days ago makes the person `cold` on the dashboard, ordered above a `due` person.
- AC-4 A follow-up with a due date 3 days out appears in the dashboard follow-ups list; completing it removes it.
- AC-5 An `intro` interaction linking A to B shows on both timelines, and B's "Intros received" count is 1.
- AC-6 Importing a 50-row CSV with 2 duplicate emails prompts on both and produces 48 or 50 people depending on the choice.
- AC-7 Searching a word that appears only in one interaction's notes returns that person.
- AC-8 Changing `lpStage` to `committed` adds the `committed_lp` role.
- AC-9 A second Clerk user sees an empty app and cannot reach the first user's rows by URL.
- AC-10 Lighthouse mobile accessibility score of 90 or higher on the dashboard and person page.

## 9. Open questions

1. Should `cold` people ever auto-archive, or only ever surface? Default: never auto-archive.
2. Is one cadence per person enough, or do LP prospects need a stage-dependent cadence? Default: one cadence, revisit after the first raise cycle.
3. Should `intro` interactions be first-class Interactions or a separate Intro entity? Default: Interaction with `introducedPersonId`, keeping v1 simple.
